# 换提示音：外部开源插件调研（2026-10-23）

> **一句话结论：我们在 `BBSound` 里手工拼字段这条路走错了 —— 有一个干净得多的挂点：
> `SBNCSoundController -canPlaySoundForNotificationRequest:`（返回 BOOL 的通知音总闸门）。**
> 在那里拦下来、自己播，比"造一个能响的 BBSound"简单一个数量级，而且失败也不会变哑巴。

本文只记录**做法与结论**。参考插件里有几个没有开源许可证（见下表），
**代码一律自己写，不复制它们的源文件**；思路与方法名属于事实，可以自由使用。

参考源码已存档在 `docs/refs/`（只作证据留存，不参与编译）。

## 二、决定性发现：`SBNCSoundController`

`SilentNotifs` 全文只有 **23 行**，核心就这一段（原文摘录，用于说明事实）：

```objc
@interface NCNotificationRequest : NSObject
@property (nonatomic, copy, readonly) NSString *sectionIdentifier;
@end

%hook SBNCSoundController
- (BOOL)canPlaySoundForNotificationRequest:(NCNotificationRequest *)request {
    if ([request.sectionIdentifier isEqualToString:@"com.apple.mobiletimer"]) {
        return %orig;                       // 闹钟不静音
    }
    BOOL shouldSilent = [[%c(SBMediaController) sharedInstance] isPlaying];
    return shouldSilent ? NO : %orig;
}
%end
```

它的 `SilentNotifs.plist`：

```
{ Filter = { Bundles = ( "com.apple.springboard" ); }; }
```

⇒ **注入 `com.apple.springboard`，arm64 + arm64e** —— 跟我们的 `NotifyBox.plist` 完全一致，
所以这个挂点对我们直接可用。

### 为什么这一个方法就够

1. **它是「总闸门」**：返回 `BOOL`，就是系统"这条通知要不要出声"的最终判定。
   拦它**不碰任何数据结构**（不用造对象、不用改字段、不用担心结构体改不了），
   所以没有 v0.0.21「挂空壳 ⇒ 整条通知变哑」那种塌方。
2. **参数就带 bundle id**：`request.sectionIdentifier` —— 正是我们做「按 App」要的东西。
   我们折腾了半天的 `BBSound` 上根本没有 bundle id。
3. **只影响声音**：横幅照常出现、振动照常（振动是另一条通道）。SilentNotifs
   用它实现「静音但通知照常弹」已经被人用了几万次。
4. **自带"不静音"先例**：闹钟走 `%orig` —— 说明"白名单放行"就是这个形状。

### 它解释了 v0.0.21 那次「完全没声音」

我们当时以为「挂了个空壳 ⇒ 系统不响」是**失败**。
从现在看，那恰好证明"改声音这件事我们是能影响到的"，只是我们想让它响别人的音。
⇒ **那一步不是白走，它是方案里"静音原声"那一半的验证。**

## 三、`NCNotificationSound.alertConfiguration` → `TLAlert`

`NotchBanners` 的 `Tweak.x.swift` 最后一段（原文摘录）：

```swift
/* Finally, create a ToneLibrary Alert (TLAlert) with the TLAlertConfiguration property
found in the NCNotificationRequest's NCNotificationSound object. */
if let alertConfig = request.sound?.alertConfiguration,
    let tl_alert = TLAlert(configuration: alertConfig) {
    //Play banner sound.
    tl_alert.play()
}
```

它的头文件（`Tweak.h`，原文摘录）：

```objc
@interface TLAlertConfiguration : NSObject
@end

@interface TLAlert : NSObject
+ (instancetype)alertWithConfiguration:(id)arg1;
- (void)play;
+ (BOOL)_stopAllAlerts;
@end

@interface NCNotificationSound : NSObject
@property (nonatomic,copy,readonly) TLAlertConfiguration * alertConfiguration;
@end

@interface NCNotificationRequest : NSObject
@property (nonatomic,copy,readonly) NSString * sectionIdentifier;
@property (nonatomic,readonly) NCNotificationSound * sound;
@property (nonatomic,readonly) NCNotificationContent * content;
@property (nonatomic,readonly) NCNotificationOptions * options;
@end
```

⇒ 三个已经确证的事实：

- `NCNotificationRequest.sound` 是 `NCNotificationSound`，它上面有 `alertConfiguration`；
- `+[TLAlert alertWithConfiguration:]` + `-play` 就能出声；
- 所以 **`alertConfiguration` 就是 iOS 16 通知音的真身** —— 这跟 v0.0.24 从真机数据
  推出的结论一致（能响的样本有 `<TLAlertConfiguration>`，我们的空壳是 nil）。
  两条独立证据对上了。

## 四、三条可走的路

| | 做法 | 依赖 | 支持自定义音频文件 | 风险 | 结论 |
|---|---|---|---|---|---|
| **A** | `canPlaySoundForNotificationRequest:` 里**自己播** + 返回 `NO` | 我们自己（AVAudioPlayer / AudioServices） | ✅ 任意格式 | 播放失败会变哑巴 ⇒ 必须做兜底 | 🟢 **推荐先走这条** |
| **B** | 在闸门里造一个 `TLAlertConfiguration` 指向我们要的音 → `TLAlert play` → 返回 `NO` | 需要 `TLAlertConfiguration` 能指向**外部文件**（未证实） | 取决于 TonesLibrary | 造 cfg 失败 ⇒ 退回 A 或原声 | 🟡 下一步，等真机接口 |
| **C** | 改 `BBSound` 的 `alertConfiguration` | 要手工造一个能响的 BB 对象 | ❌ 未知 | v0.0.21 实测：造错就整条哑 | 🔴 放弃，v0.0.21~v0.0.24 一直在这一栏 |

**为什么 A 能同时支持「系统内置音」和「自定义文件」**：
系统内置通知音的文件就在 `/System/Library/Audio/UISounds/` 下（`.caf`）。
⇒ 用户选「三全音」= 播那个 `.caf`；选「我自己的 mp3」= 播那个 mp3。
**统一种类：一切当文件播**。这样两套逻辑合成一套，不需要 TonesLibrary 任何东西。

## 五、A 方案的关键设计（防"变哑巴"）

绝不能"先掐原声、再尝试播" —— 那中间失败了就是静音。**顺序必须反过来：**

```objc
%hook SBNCSoundController
- (BOOL)canPlaySoundForNotificationRequest:(NCNotificationRequest *)request {
    NSString *bid = request.sectionIdentifier;
    if (!NBIsSoundTargetBundle(bid)) {
        return %orig;                       // 没配自定义音：一动不动
    }
    BOOL started = NBPlayCustomSoundForBundle(bid);   // 先把我们的音播起来
    if (!started) {
        return %orig;                       // 🔴 没播起来 ⇒ 老老实实放原声
    }
    return NO;                              // 播起来了 ⇒ 掐掉原声，避免双响
}
%end
```

**判据：`started == NO` 时必须回到 `%orig`。**
这样"功能没生效"最坏也就是"还是原声"，绝不会让用户漏消息。

### 播放实现（两层）

| 层 | 用什么 | 适用 | 注意 |
|---|---|---|---|
| 主 | `AVAudioPlayer` | mp3 / m4a / wav / caf / aiff | 要处理 audio session（见下） |
| 备 | `AudioServicesCreateSystemSoundID` + `AudioServicesPlaySystemSound` | caf / aiff / wav，≤30s | 自动遵循静音开关，不碰 session |

`AVAudioPlayer` 在 SpringBoard 里的 session 处理：
用 `AVAudioSessionCategoryAmbient` + `MixWithOthers`（**会被静音开关静音、不打断正在播的音乐** ——
这正是通知音该有的语义）。**只设一次**（`dispatch_once`），不要每条通知来回改。

### 其它必须处理的
- **连续多条通知**：前一个 player 还没播完。要么打断旧的，要么小型池（最多留 3 个）。
- **锁屏状态**：走同一个闸门，无需特殊处理。
- **静音开关**：`Ambient` 会自动遵循，不用自己判断。
- **音频文件位置**：要放在 SpringBoard 能读、盒子 App 也能写的共享目录
  （不能放 App 沙盒里 —— 路径里有随机 UUID）。用我们 Store 已经在用的数据目录。

## 六、v0.0.25 要做什么

1. **侦察**（只读，写文件）：dump `SBNCSoundController` 的完整实例方法表，
   确认 `canPlaySoundForNotificationRequest:` 真名与全部同类方法（可能还有
   `shouldVibrateForNotificationRequest:` / `-playSoundForNotificationRequest:` 等，
   知道全貌才好定挂点）。
2. **挂闸门**：按上面第五节的顺序实现，配了自定义音的 App 才生效。
3. **三态自证**（每条都留痕，用户靠听感 + 日志就能定位）：
   - `SOUND# 闸门被调用 bid=… orig=1/0` —— 证明挂上了；

   - `SOUND# 本次放行原声（没播起来 / 没配）` —— 证明兜底走了哪条。
4. **崩了要能自愈**：已经有 `.sound_guard` 那套，继续复用。

## 八、对之前几轮的修正

- v0.0.21「挂空壳 ⇒ 完全没声音」**不是纯失败**：它验证了「我们能影响通知出不出声」。
- v0.0.23 的 `repeats` / `maxDuration` 方向作废（已确认）。
- v0.0.24 把 `alertConfiguration` 当成"唯一的活路"——**这个判断只对了一半**：
  `TLAlertConfiguration` 确实是真身，但**不一定需要我们自己造它**；
  只要拿到通知请求，系统和它自己的 cfg 都在手上（`request.sound.alertConfiguration`）。
- 真正被忽略的是：**`SBNCSoundController` 这个闸门从没进过我们的侦察清单**。
